# データ仕様

← [outline.md](outline.md)

## 1. 保存先

データはローカルファイルとして保存される。

- ワークスペースディレクトリ（利用者が選んだ任意のフォルダー）
  - `<workspace>/_workspace.md` … ワークスペース自身（ルートノード）
  - `<workspace>/<project>/_project.md`、`<workspace>/<project>/<node-id>/_index.md` … ノードの**正本**。1 ノード 1 ファイルの Markdown で、旧 Markdown 形式と同じ置き場所・同じ書き方（§ 3）
  - ノードのフォルダーの `assets/`・`attachments/` … 本文に貼った画像と添付ファイル（§ 4）
  - `<workspace>/.task-manage/` … アプリの作業用。元に戻す履歴・削除したノードのごみ箱・グラフビューの座標（§ 3.5、§ 3.7）
- アプリのデータディレクトリ
  - `meta.json` … テーマ・表示設定・登録済みワークスペースなど、アプリの設定（§ 2）
  - `window-state.json` … メインウィンドウの大きさ・位置・最大化状態。起動時に BrowserWindow を作る前へ読むため `meta.json` から分離している

アプリのデータディレクトリは次の順で決まる（`electron/app-paths.js`）。

1. `TASK_MANAGE_DATA_DIR` 環境変数があればそこ。テストとエージェント検証はこれで利用者のデータから切り離す
2. ポータブル版（配布版で、実行ファイルと同じフォルダに `data` フォルダがある）はその `data`。起動直後に Electron の利用者データ領域ごと `data` へ移すので、設定ファイルに加えて renderer の localStorage・キャッシュ・ログも `data` に入る
3. インストーラー版は OS の利用者データ領域（`app.getPath("userData")`。Windows なら `%APPDATA%\task-manage`）。インストール先は書き込めないことがあり、更新やアンインストールで消えるので使わない
4. 開発中（`app.isPackaged` が偽）は `electron/`（git 管理外）

リリースのポータブル版（`task-manage-<version>.tar.gz`）には空の `data` フォルダが入っている。新しい版に移るときは、古い版の `data` フォルダを新しい版のフォルダへ上書きコピーすれば設定を引き継げる。`data` を消すと `%APPDATA%` を使うようになる。

0.1.45 までの配布版は設定をアプリのフォルダ（`resources/app/electron/`）に置いていたため、更新のたびに消えていた。

以前の版が使っていた `electron/db.json`（アプリ内プロジェクト）は読まない。ワークスペース直下の旧 Markdown プロジェクト（`<dir>/_project.md`）は、そのまま開ける（§ 7.1）。`.task-manage/graph-v1.json`（1 つの JSON にすべてを入れていた形式）は、開いたときに一度だけ Markdown へ変換する（§ 7.2）。

## 2. meta.json

`meta.json` は、アプリの設定を持つオブジェクトである。main プロセスの `electron/settings-store.js` が起動時に読み、変更は少し待ってまとめて書く（一時ファイルへ書いてから置き換える）。壊れたファイルは消さずに `meta.json.broken-<時刻>` へ退避し、初期値で起動する。

```json
{
  "theme": "light",
  "workspaces": [{ "path": "C:\\Users\\me\\Tasks", "label": "Tasks" }],
  "activeWorkspace": "C:\\Users\\me\\Tasks",
  "preferences.date_time_format": "slash",
  "closed_paths_8e392450-20f7-479a-a7f2-38bdafb913df": [],
  "show_archived_8e392450-20f7-479a-a7f2-38bdafb913df": false
}
```

- `theme`
  - アプリ全体のテーマ（`"dark"` / `"light"`）。変わると開いている他のウィンドウにも反映する
- `workspaces` / `activeWorkspace`
  - 登録済みワークスペースと、いま開いているもの。新しいパスはフォルダー選択ダイアログで選ばれたものだけ登録できる（レンダラーが任意のパスを登録することはできない）
- `preferences.date_time_format`
  - 入力ショートカット（`Ctrl+;` / `Ctrl+:`）でテキスト入力に挿入される書式。`"slash"`（既定、`2026/05/26`）/ `"iso"`（`2026-05-26`）/ `"japanese"`（`2026年5月26日`）のいずれか
- `closed_paths_<スコープID>`
  - そのスコープ（開いているプロジェクト）で閉じている**行（経路）**の一覧
- `show_archived_<スコープID>`
  - アーカイブ済みを表示するか

ノードは親を複数持てるため、同じノードが親ごとに複数の行として現れる。開閉はノードではなく**行＝辺**ごとの状態なので、キーにはノード ID ではなくルートからの経路（`ルートID/親ID/子ID`）を使う。片方の親の下で閉じても、もう片方の親の下は開いたままになる。

## 3. ノードのファイル（正本）

ワークスペースの正本は、フォルダーの中の Markdown ファイルである。**1 ノード 1 ファイル**で、置き場所も書き方も旧 Markdown 形式と同じ。人も生成 AI も、そのまま読める（本文は frontmatter の後ろにそのまま書かれ、画像は相対パスで参照される）。グラフの機能（複数の親・親ごとの並び順・辺だけのアーカイブ・循環）は frontmatter の `parents:` に入る。設計の背景は [node-graph-design.md](node-graph-design.md)。

```
<workspace>/
├── _workspace.md               ← ワークスペース自身（ルートノード）。本文・タグ・添付も持てる
├── <project>/                  ← ワークスペース直下に作ったノード（プロジェクト）のフォルダー
│   ├── _project.md             ← そのノード
│   ├── assets/ attachments/    ← そのノードの画像と添付
│   └── <node-id>/
│       ├── _index.md           ← 通常のノード
│       ├── assets/ attachments/
├── _inbox/                     ← Inbox もプロジェクトと同じ形（`_project.md` に `kind: inbox`）
└── .task-manage/               ← アプリの作業用（§ 3.5、§ 3.7）
```

```markdown
---
id: t-top
name: トップページ実装
status: In Progress
start: 2026-09-01
due: 2026-10-01
parents:
  - id: p-web
    order: 1
  - id: t-design
    order: 0
    archived: true
    archived_at: 2026-09-20T01:00:00.000Z
tags:
  - frontend
created: 2026-09-02
attachments:
  - name: 仕様書.pdf
    path: ./attachments/仕様書.pdf
    size: 12345
---

# メモ

本文（Markdown）。画像は ![図](./assets/diagram.png) のように相対パスで参照する。
```

### 3.1 frontmatter のキー

| キー | 意味 |
| --- | --- |
| `id` | ワークスペース内で一意の不変 ID。**これが無いファイルはノードとして読まない** |
| `name` | 名前 |
| `status` | ステータス。キーが無いのは「ステータスなし」（§ 5） |
| `start` / `due` | `YYYY-MM-DD`。両方あるときは `start <= due` |
| `parents` | 親への辺の配列（§ 3.3）。短縮形 `- <親ID>` も読む |
| `tags` | タグ。前後の空白・先頭の `#` を落とし、大文字小文字を無視して重複排除する。`tags: [a, b]` やカンマ区切りも読む |
| `created` | 作成日 `YYYY-MM-DD`（旧形式の `createdAt:` も読む） |
| `archived` / `archived_at` | ノードごとのアーカイブ（子孫へは伝播しない） |
| `format` | 本文の形式。`quill` のときだけ書く（既定は markdown。§ 6） |
| `kind` | Inbox のノードにだけ `inbox` |
| `attachments` | 添付の一覧 `[{ name, path, size }]`（§ 4）。キーが無い旧形式のファイルは、`attachments/` フォルダーの中身が一覧になる |
| `order` | 旧形式の、プロジェクトのルートの並び順。`parents` が無いファイルのときだけ読む |

- 書き方は標準的な YAML として読める形にする。`name: "Bug: login fails"` のように、`: ` や先頭が記号の値など、引用符なしで書くと別の意味に読まれうるものだけ引用符で囲む。引用符なしで書かれた旧形式の値も読める
- アプリが知らないキー（手や他のツールが足したもの）は、そのノードを書き戻すときも元の行のまま残す
- 本文の前後の空白は読むときに落とす

### 3.2 置き場所

ファイルの置き場所は、ノードを作るときに決め、あとから変えない。名前を変えても、親を付け替えても動かさない（ツリーの形は置き場所ではなく `parents:` が表す）。

- ワークスペース直下に作ったノード（プロジェクト）: `<名前を小文字・ハイフンにしたもの>/_project.md`。同じ名前があれば `-2`、`-3`…（大文字小文字は区別しない）
- それ以外: 最初の親と同じプロジェクトのフォルダーに `<id>/_index.md`。コピーで増えたノードは、コピー先の親のプロジェクトに置く
- フォルダーは 2 段（プロジェクト → ノード）まで読む。`.` で始まる名前、`assets`・`attachments`・`node_modules` はプロジェクトとして調べない

このため、プロジェクトを別のノードの子へ移したり、ノードをワークスペース直下へ出したりすると、フォルダーの位置と見かけの階層は一致しなくなる。階層は `parents:` を見ること。

### 3.3 親子関係（辺）

- 辺は子側の `parents` に持つ。子は複数の親を持てる（多親）。ワークスペース直下の子（プロジェクト）も、ワークスペース自身への辺を `parents` に持つ
- 並び順は**辺の属性**なので、親 id と組で `order` に持つ。同じノードが親ごとに違う位置を取れる。`order` の無い辺は「末尾」（読み込み時に、兄弟の末尾から id の昇順で番号を付ける）
- `archived: true` が付いた辺は「その親の下からだけ片付けた」ことを表す。ノード自体の `archived` とは独立
- 自己接続と、同じ親子の重複は保存できない
- 複数ノードからなる循環は保存できる（グラフビューからだけ作れる）。ツリーとファインダーは、いま辿っている経路の祖先に戻った時点で「循環参照」として打ち切る
- どのノードもルートから辿れる。辺の削除やノード削除で辿れなくなったまとまりには、ルートからの入口になる辺を決定的に補う（`repairRootReachability`）

### 3.3.1 読み込みでは frontmatter までしか読まない

アプリは、ノードのファイルの**先頭の frontmatter だけ**を読み、本文は読まない（本文の遅延ロード）。ノードは `bodyLoaded: false` で、`body` を持たない。ノード数が多くても、読む量はファイルの大きさ（本文）に依らない。

- 先頭の 4 KB を読み、frontmatter を閉じる `---` の行が見つかるまで、読む量を 4 倍にして先頭から読み直す。ファイルの終わりまで読んでも閉じる `---` が無ければ、読めた分をそのまま解釈する。frontmatter の解釈は、全文を読んだときと変わらない（同じ範囲を同じ規則で読む）
- 旧メモは、`title:` が無いと本文の最初の見出しが名前になるので、その場合だけ全文を読む
- 本文は、必要になったときに読む。ノードの詳細を開いたとき（`ws:read-node-body`）、本文の検索をオンにしたときと全メモの形式変換のとき（`ws:read-all-node-bodies`）
- 本文を使う操作は、実行の前にそのノードの本文を読む。本文を変える・形式を変える `update-node`（元に戻すのために元の本文が要る）と、`copy`（コピー元と、子孫ごとのコピーなら子孫の本文）。読めなければ操作ごと止める
- 本文を読んでいないノードを書き戻すときは、**ディスクの本文をそのまま残す**。本文を読めなければ保存しない（空の本文で上書きしない）。元に戻す履歴のパッチにも、読んでいない本文は入れない
- 読み込みの前倒し: アプリは、Electron の起動（ready）を待たずに、設定（`meta.json`）にある開いているワークスペースの読み込みを始める（`electron/early-read.js`）

全文を読む読み込み（`loadWorkspaceSync`、テストとツール用）は、これまでどおり本文まで読む。

### 3.4 読み込み時の修復

フォルダーは、人や生成 AI が置いたものでも、別の PC から写したものでも、旧バージョンが書いたものでもある。開けなくなるのではなく、読み込み時に直して開く（`electron/store/loader.js`）。直した内容はログに警告として残る。

| 状態 | 直し方 |
| --- | --- |
| `_workspace.md` が無い | 新しい id で作る（初回だけ書く） |
| 別のプロジェクトと id が重複 | 後から読んだ方に、ファイルの場所から決めた新しい id を振る。そのプロジェクトの中の参照も合わせる。ファイルにも書く |
| 同じプロジェクトの中で id が重複 | 後から読んだ方に新しい id を振る。ファイルにも書く |
| 親が見つからない・親が無い | そのノードが属するプロジェクトのルートの子にする（プロジェクトのルート自身ならワークスペース直下） |
| ルートから辿れない | ルートからの入口になる辺を補う（§ 3.3） |
| 並び順が無い辺 | 兄弟の末尾から番号を付ける |
| 日付・ステータスの誤り | その値を捨てる（開始日が期限日より後なら開始日を捨てる）。ファイルは、そのノードを次に保存するまで変わらない |
| `id` の無いファイル | 読まない（ファイルには触れない） |
| 旧メモ（`<dir>/<memo>.md`） | ノードとして読む（§ 7.1） |

### 3.5 リビジョンと履歴

- 書き込みはワークスペースごとに 1 本の列に並ぶ（`electron/workspace-graph.js` の `enqueue`）。グラフはメモリ上に持ち、操作はそのグラフにエンジンが行い、**変わったノードのファイルだけ**を書く
- `revision` はメモリ上の数で、起動のたびに 0 から数える（ファイルには書かない）。レンダラーは操作のたびに、手元のグラフの `revision` を添えてコマンドを送る。違えば `Workspace graph changed` で拒否し、何も書かない。レンダラーは最新を読み直して知らせる。ディスクから読み直しても `revision` は戻らず、進む
- 元に戻す / やり直しの 1 段は、戻すのに要るノードと欄だけのパッチ `{ nodes: { [id]: node | null }, fields: { [key]: { value } | null } }` を、1 段 1 ファイルで `.task-manage/history/undo/<seq>.json`（やり直しは `redo/`）に書く。最大 50 段。再起動しても残る。新しい操作をするとやり直し履歴は捨てる
- ノードを消す（元に戻すで作成を取り消す場合も同じ）と、そのノードのフォルダー（画像・添付を含む）を `.task-manage/trash/<seq>/<node-id>/` へ移す。履歴の同じ段を戻す（やり直す）と、元の場所へ戻る。履歴から消えた段のごみ箱は片付ける。旧メモのファイルと、プロジェクトのルートを消すときは、そのノード自身のファイルだけを移す
- 複数のファイルにまたがる操作が途中で失敗したら、書いたものを巻き戻し、グラフも履歴も変えない
- **アプリの外で書き換えられたファイル**は上書きしない。保存の直前に、そのファイルを読み直して、最後に読んだ・書いたものと同じかを確かめ、違えば「ファイルがアプリの外で変更されています」と知らせて何も書かない（日時だけが変わった場合は問題にしない）。照合は frontmatter と本文を別々に行う。frontmatter は必ず照合する。本文は、アプリが読んでいる（照合の値がある）ときだけ照合する。読んでいない本文は、ディスクの最新のものをそのまま残すので、外で書き換えられていても構わない。ワークスペース管理画面の「読み込み直す」で、ディスクの内容を取り込める。アプリを開いている間の外での変更は、そのときまで画面に出ない（ファイルの監視はしない）
- 操作の結果と他のウィンドウへの通知は、グラフ全体ではなく**変わったノードだけ**（差分）。画面は持っているグラフにそれを当てる。間の更新を取りこぼしたときだけ、全体を読み直す

### 3.6 操作（コマンド）

操作はすべて main プロセスのグラフエンジン（`electron/workspace-graph-engine.js`）を通る。レンダラーはツリーや木の形を保存しない。

| コマンド | 意味 |
| --- | --- |
| `create-node` | 親の下にノードを作る |
| `update-node` | ノードの欄を変える |
| `link` / `detach` / `move` | 辺を足す／外す／付け替える（他の親と子孫の関係は残る） |
| `archive-edge` | その辺だけアーカイブ／復元する |
| `delete-node` | ノード自身とその辺を消す。子孫は消さない |
| `copy` | `node`（そのノードだけ）／`share-children`（直下の子を共有）／`subgraph`（子孫ごと） |
| `set-position` | グラフビューでの座標 |
| `batch` | 複数のコマンドを 1 つの操作（1 回の「元に戻す」）としてまとめる |

ルート（ワークスペース自身）は親を持たず、削除・移動・複製・アーカイブできない。Inbox も削除・アーカイブ・移動できない。

### 3.7 グラフビューの座標

`.task-manage/layout.json` に `{ "positions": { "<node-id>": { "x": 0, "y": 0 } } }` を書く。ノードのファイルには入れない。元に戻すの対象。

## 4. 画像と添付

- 置き場所はノードのフォルダー。本文に貼った画像は `assets/`、添付ファイルは `attachments/`。プロジェクトのルートなら、プロジェクトのフォルダー直下の同名のフォルダー
- 本文からは、ノードのフォルダーからの相対パス `![](./assets/<file>)` で参照する。ふつうの Markdown ビューアでも表示できる。プレビュー時は main プロセスが画像を読み、`data:` URL にして返す（`ws:resolve-graph-asset`）。画像以外は返さない
- 添付の一覧は frontmatter の `attachments:`（`name` / `path` / `size`）。一覧から外しても実ファイルは消さない（元に戻したときに添付を戻せるようにするため）。0 件のときも `attachments: []` と書く（書かないと、旧形式と同じく、フォルダーの中身が一覧として現れる）
- ファイル名は元の名前を残し、同じ名前があれば `-2`、`-3`…を付ける。貼り付けた画像は `pasted-<時刻>-<乱数>.<拡張子>`
- ノードをコピーすると、画像と添付の実体もコピー先のフォルダーへ写す。元のノードを消してもコピーから使える
- ノードを消すと、フォルダーごとごみ箱へ移り、元に戻すと画像・添付も戻る（§ 3.5）
- パスはそのノードの `assets/`・`attachments/` の中だけを許し、外へ出る参照・シンボリックリンク経由の脱出は拒否する

## 5. ステータス

| 意味 | 保存値 |
| --- | --- |
| 進捗管理をしない | 省略（`status` 欄を書かない） |
| 進捗管理の対象だが、状態は未決定 | `Undefined` |
| 未着手 / 保留 / 進行中 / 完了 / キャンセル | `Open` / `Pending` / `In Progress` / `Completed` / `Canceled` |

### 5.1 「なし」は既定値ではなく状態のひとつ

同じツリーに「期限とステータスで追跡するノード」と「ただ書いてあるノード」が並ぶ。後者に既定のステータスを与えると、ノート 1 つ 1 つが「未着手」として積み上がり、ステータス列も絞り込みも意味を失う。だから「なし」は `Open` へのフォールバックではなく、対等な状態として扱う。

- **保存では欄ごと書かない。** 空文字を書くと、次に読んだとき「値がある」と「無い」を区別できなくなる
- **読みで `Open` を埋めない。** 日付を付けてもステータスを自動で付けない
- **レンダラー側では空文字**（`NO_STATUS`）で表す。ステータスは選択コントロールの値として往復するため。境界での変換は `tree_projection.js` の `projectTreeGrid`（省略 → `""`）と `nodeChanges`（`""` → 省略）の 2 箇所だけ
- 絞り込みは**完全一致**で見る。部分一致だと、あらゆる文字列が空文字を含むので「なし」で絞ったときに全行が残ってしまう
- 選択済みステータスを取り出すときに `filter(Boolean)` を使わないこと。「なし」は空文字なので落ちる
- 並べ替えでは「なし」を最後に置く
- 回帰テストは `tests/unit/no_status.test.ts`

## 6. ノードの本文

**1 つのメモ ＝ 1 つのノード。** ノードは本文を 1 つだけ持ち、複数の記録は子ノードで表す。

- `body` — 本文そのもの（Markdown なら文字列、Quill なら Delta）
- `format` — `"markdown"` または `"quill"`。省略時は `"markdown"`。新しく作るノードも `"markdown"`

### 6.1 形式の変換

- **個別変換**：ノード詳細の「形式を変換」で Markdown ⇄ Quill を切り替える。中身があるときは、装飾や埋め込みが落ちうることを確認する。**本文が空なら確認を出さない**
- **一括変換**：ツールバーのメニューで、開いているプロジェクトの全ノードの本文を変換する。**本文が空のノードは対象にしない**。多親ノードは 1 回だけ数える
  - 変換内容の警告フェーズと、完了結果フェーズを持つモーダルで確認する
  - 全体の変換は 1 つの操作として保存され、1 回の「元に戻す」で戻せる

### 6.2 Markdown プレビュー

- 見出し、箇条書き、引用、コード、表などの GitHub Flavored Markdown
- task list / Markdown 画像記法
- 子ノードへの `[[Wiki Link]]` と `[[Wiki Link|Alias]]`、外部 URL への wiki link
- 貼り付けた画像はノードのフォルダーの `assets/` に保存し、本文には `![](./assets/<file>)` を挿入する
- 外部 URL と `data:` URL はそのまま表示する

旧 Quill 形式の Delta オブジェクト（`{ ops: [...] }`）が Markdown の本文に残っている場合は、表示時に `ops[].insert` を連結してプレーンテキストへ変換する。それ以外の非文字列値は後方互換用に JSON 文字列として表示する。

## 7. 旧形式との関係

### 7.1 旧 Markdown 形式のフォルダー

以前の版が書いていた、プロジェクトごとのフォルダーと Markdown ファイルは、**そのまま開ける**（取り込みの操作は要らない）。置き場所も書き方も § 3 と同じで、違いは次のとおり。

- ワークスペースの `_workspace.md` が無い → 初めて開いたときに作る
- プロジェクトのルート（`_project.md`）に `parents` が無い → ワークスペース直下の子として読み、`order` を並び順にする
- `attachments:` が無い → `attachments/` フォルダーの中身が添付の一覧
- 旧メモ（`<node-dir>/<memo-id>.md`）はノードとして読む。そのノードの子ノードになり、`title` → 名前（無ければ先頭の見出し、それも無ければ `memo`）、本文 → `body`、`tags` → タグ。ステータスは与えない。並びは実ノードの子の後ろ。**そのノードを保存するとき**に、自分のフォルダー（`<project>/<id>/_index.md`）へ移る。本文が参照している画像は新しいフォルダーへ写し、元のメモのファイルは消す。危険な id（`../` を含むなど）のメモは、中身を捨てずに id だけ振り直す。ワークスペース直下の `.md`（README など）は、ノードとして読まない
- `status:` の無いファイルは「ステータスなし」として読む

読んだだけではファイルを書き換えない（書くのは、初回の `_workspace.md` と、id を振り直したノードだけ）。ノードを編集すると、そのノードのファイルだけが現在の書き方に直る。

新しいプロジェクトのフォルダーを、アプリを開いている間にワークスペースへ置いたときは、ワークスペース管理画面の「読み込み直す」で取り込む。

### 7.2 graph-v1.json からの変換

以前の版は、ワークスペースの内容をすべて `.task-manage/graph-v1.json` 1 つに入れていた（本文・履歴を含む）。編集のたびにこのファイル全体を書き直すため、ノードと本文が増えるほど操作が重くなっていた。

`graph-v1.json` があるワークスペースは、開いたときに一度だけ Markdown へ変換する（`electron/store/migrate-graph-json.js`）。

- 元のものは消さない。`graph-v1.json` は `graph-v1.json.migrated` に名前を変え、`.task-manage/assets/` はそのまま残す（不要になったら利用者が消してよい）
- 取り込み元だった旧 Markdown のフォルダー（ワークスペース直下で、ルートの id がグラフにあるもの）は、`.task-manage/backup/legacy-markdown-<時刻>/` へ移してから、グラフの内容で書き直す。古いファイルが残ると、グラフで消したノードが読み込みのたびに戻ってくる。グラフに入っていない旧フォルダーはそのまま置き、プロジェクトとして読む
- 書く場所は § 3.2 のとおり。プロジェクトのフォルダー名は、取り込み元のフォルダー名があればそれを使う
- `.task-manage/assets/<id>/` の画像と添付は、各ノードのフォルダーへ写し、本文と添付の参照を相対パス（`./assets/...`・`./attachments/...`）に直す。保存時に付けていた id の接頭辞は外す
- 元に戻す / やり直しの履歴は引き継がない
- 途中で止まっても、次に開いたときに続きから変換する（`.task-manage/migration.json` に書き終えたフォルダーを記録する）

回帰テストは `tests/unit/markdown-format.test.js`・`tests/unit/markdown-loader.test.js`・`tests/unit/workspace-graph-persistence.test.js`・`tests/unit/workspace-graph-migration.test.js`。
